# LarpCode macOS — security and privacy notes (v1)

This document describes the behaviour that exists in this repository for the macOS edition. It is
based on `PORT_SPEC.md` (the source of truth for v1), the release workflow in
`.github/workflows/release.yml`, `script/macos/entitlements.plist`, `script/stage-macos.ts`, and the
launchers in `shortcuts/`. Where a property is not established by those sources, it is listed under
[What is not guaranteed](#what-is-not-guaranteed) instead of being asserted.

## Local-first behaviour

The application and its agent runtime run on the Mac. Sessions, settings, caches, and state are
written to local directories under `~/Library/Application Support/LarpCode macOS/` and
`~/Library/Caches/LarpCode macOS/` (see [Data isolation](#data-isolation-from-upstream-opencode)).
No AI model or API key is bundled with the app; a provider must be configured before model requests
can be made.

"Local-first" here means that files and prompts are handled locally until a request is deliberately
sent to a service. It does **not** mean the app makes no network requests at all:

- **Provider requests** are sent when a prompt/model request is made to a configured provider.
- **Free/fallback routing** is a configured behaviour: free models use opencode.ai's shared
  anonymous pool, and when Free fallback is enabled a refused request can be routed to a configured
  DeepSeek key or to Pollinations (`text.pollinations.ai`). The TUI/CLI reports when a fallback is
  used.
- **Update checks** read `update.json` from the release feed; the first check happens automatically,
  and `larpcode upgrade` or `/update` checks manually. The in-app updater is pointed at this
  repository's release feed, never at the Windows `LarpCode-Setup.exe` asset.
- **Optional routing** (Tor, SOCKS5) is reported by `larpcode doctor` / `larpcode settings` as an
  optional helper and is off unless configured.

Providers are not contacted on the user's behalf for purposes other than these configured or
user-initiated actions. The app does not ship credentials for any provider.

## v1 is unsigned and not notarized

The v1 desktop and CLI binaries are **unsigned and not notarized**. Concretely:

- There is no Developer ID signature on the app or DMG, so Gatekeeper identifies it as coming from
  an unidentified developer and may block the first launch when the download carries a quarantine
  attribute.
- There is no notarization ticket and no stapled ticket on the DMG/ZIP, so Apple has not recorded a
  notarization result for these artifacts.
- The release workflow's signing/notarization steps are conditional. If any signing secret is
  absent, the build takes the "skip" path and still produces the release assets. For v1, the
  expected outcome is unsigned artifacts.

The only integrity signal published with the release is the checksum file described below. Opening
an unsigned app requires an explicit user action; see [Gatekeeper and quarantine](#gatekeeper-and-quarantine).

## Verify downloads with SHA256SUMS

Every binary asset is listed in `SHA256SUMS`, generated by `script/stage-macos.ts` and published on
the release. To verify, download the asset and `SHA256SUMS` from the
[latest release](https://github.com/Aero-Apex/LarpCode-MacOS/releases/latest), put them in the same
folder, and run from that folder:

```sh
shasum -a 256 -c SHA256SUMS
```

Each line should end in `OK`. Keep the published filename unchanged — for example
`LarpCode-macOS-universal.dmg` — because the checksum file matches on exact names. The publish job
runs the same check (`shasum -a 256 -c SHA256SUMS`) before creating the release.

The CLI installer performs its own check against `cli.json`, which contains `version`, `name`, and
`sha256` for the `larpcode` binary, and aborts on a mismatch. `update.json` contains `version`,
`notes`, `url`, and `zipUrl`; it has no signature field.

Checksums confirm that a downloaded file matches the file published in the same release. They do
not establish who published it or whether the code is safe.

## Gatekeeper and quarantine

When macOS blocks the first launch, either:

1. In Finder, **Control-click** (or right-click) **LarpCode macOS.app**, choose **Open**, then choose
   **Open** again in the dialog; or
2. Remove the quarantine attribute from a terminal, quoting the path because it contains a space:

   ```sh
   xattr -dr com.apple.quarantine "/Applications/LarpCode macOS.app"
   ```

   Then open the app normally.

Use these steps only for an app downloaded from the official Releases page, and only after checking
its checksum. Removing the quarantine attribute is a per-copy action: a newly downloaded or upgraded
copy can be quarantined again and require the same step.

## Optional codesign and notarization hooks

The release workflow supports signing when all four GitHub Actions secrets are set. If **any** of
them is missing, the workflow logs a notice and skips codesign/notarization; the build does not
fail.

| Secret | Used for |
| --- | --- |
| `MACOS_SIGN_IDENTITY` | Identity passed to `codesign --sign` (a Developer ID Application identity) |
| `MACOS_NOTARIZE_APPLE_ID` | Apple ID passed to `xcrun notarytool submit --apple-id` |
| `MACOS_NOTARIZE_TEAM_ID` | Team ID passed to `--team-id` |
| `MACOS_NOTARIZE_PASSWORD` | App-specific password passed to `--password` |

When all four are present, the workflow signs each DMG/ZIP with `codesign --force --sign
"$MACOS_SIGN_IDENTITY" --options runtime --timestamp`, submits it with `xcrun notarytool submit
--wait`, and staples the result with `xcrun stapler staple`. If no DMG/ZIP is found under `dist`, it
skips with a notice.

Two operational points visible in the workflow:

- The workflow does not import a signing certificate into the runner keychain. The named identity
  must already be available there, or `codesign` will fail when the secrets are set.
- Notarization requires an Apple Developer Program account and an app-specific password for the
  Apple ID. These are maintainer-side credentials, not distributed to users.

The hooks change what is produced; they do not retroactively sign v1 artifacts already published.

## Entitlements overview

`script/macos/entitlements.plist` is provided for a future hardened-runtime signature. The keys:

| Key | What it requests |
| --- | --- |
| `com.apple.security.cs.allow-jit` | JIT memory, used by JavaScript/Electron runtimes |
| `com.apple.security.cs.allow-unsigned-executable-memory` | Creation of unsigned executable memory by the runtime |
| `com.apple.security.cs.disable-library-validation` | Loading of libraries that are not signed by the same team |
| `com.apple.security.device.audio-input` | Microphone/audio input access |
| `com.apple.security.files.user-selected.read-write` | Read/write access to files the user selects |
| `com.apple.security.network.client` | Outbound network connections (for example, provider requests and update checks) |
| `com.apple.security.network.server` | Inbound/local listening sockets |

There is no App Sandbox entitlement and no blanket home-directory file entitlement. These entries
are a template for a future signed build: the v1 binaries are unsigned, so hardened runtime and
these entitlements are not applied to them. `disable-library-validation` also relaxes a hardened
runtime protection when it is used, by permitting libraries outside the signing team's control.

## Data isolation from upstream OpenCode

Both macOS launchers set the XDG variables used by the CLI/upstream code to LarpCode-specific
paths:

```
XDG_DATA_HOME   = "$HOME/Library/Application Support/LarpCode macOS/xdg/data"
XDG_CONFIG_HOME = "$HOME/Library/Application Support/LarpCode macOS/xdg/config"
XDG_CACHE_HOME  = "$HOME/Library/Caches/LarpCode macOS/xdg/cache"
XDG_STATE_HOME  = "$HOME/Library/Application Support/LarpCode macOS/xdg/state"
```

These values are set by `shortcuts/LarpCode.command` (desktop launcher) and `shortcuts/larpcode`
(CLI shim); both create the directories and export the variables before starting the app or CLI.
The desktop and CLI installs share these locations. Because of the isolation, LarpCode does not
read or overwrite the data of an OpenCode installation on the same machine. The paths contain a
space, so they are quoted everywhere in the launchers and in any manual commands.

The `opencode` URL scheme is kept for session compatibility; that is a scheme name, not shared
storage with upstream OpenCode.

If the `.app` bundle is launched directly instead of through the provided launcher, these XDG
variables are not set by the launcher; use the provided launcher when this isolation matters.

## What is not guaranteed

- **No code identity or Apple review in v1.** Unsigned, unnotarized binaries carry no Developer ID
  identity, no notarization ticket, and no Apple malware-check record. Gatekeeper warnings are a
  warning about provenance, not a determination that the app is safe or unsafe.
- **No authenticity from checksums.** `SHA256SUMS` and `cli.json` verify integrity against the
  published files. If the release page or the published files were replaced, matching checksums
  would still be produced. There is no signed release manifest.
- **No guarantee of no network traffic.** Provider requests, the automatic first update check,
  manual update checks, and configured free/fallback routing all use the network. No claim is made
  that requests are end-to-end encrypted, that providers do not retain them, or that third-party
  providers follow any particular policy.
- **No guarantee that Tor/SOCKS5 covers all traffic.** These are optional helpers whose presence is
  reported by `larpcode doctor` / `larpcode settings`; no claim is made that every connection is
  routed through them.
- **No sandbox or at-rest encryption guarantee.** No App Sandbox entitlement is present, and v1 is
  unsigned so the hardened-runtime file restrictions are not enforced. No keychain storage or
  encryption of local sessions/settings/caches is specified. Other components (plugins, tools, or
  the OS) may write logs or crash reports outside the XDG directories listed above.
- **No signed update channel.** `update.json` has no signature field; the in-app updater trusts the
  release feed URL. The CLI installer verifies the CLI binary hash from `cli.json`, but the update
  feed itself is not signed.
